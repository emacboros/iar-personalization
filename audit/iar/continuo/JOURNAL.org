* 2026-09-03 cycle 11 -- the fence that fired into the void now fires

The thread was the red test from cycle 10, and the mechanism was
exactly the hypothesis: the warn branch returned (list :block ...)
but the soft-cap `when` followed it in the same body, so at the warn
count the function's return was nil -- the block was computed and
thrown away. The fix is the generalization cycle 10 named: the block
must BE the return. or-wrap the warn and cap branches.

Two things the fix surfaced that the roadmap hadn't predicted:

1. `=` had to become `>=`. With `=`, a memory tool landing exactly
   at the warn count (count=60, tool=append_file) skips the warn
   branch entirely, then :cap-warned is never set, then every later
   call re-tests `= 60` and fails -- the warning never fires for
   that cycle at all. A fence that can be skipped by one unlucky
   call ordering is not a fence.

2. The warn needed a window. With the or-wrap in place, the warn
   branch would have fired at count 121+ (>= 60, not yet warned) and
   told a past-cap cycle "this call was NOT lost -- retry it" -- a
   lie, since the cap branch's landing demand is the truth at that
   point. Warn window is now [60, 120]: past the cap, the urgent
   message wins.

* 2026-09-03 cycle 3 -- the guard that never escalated

The thread was the chain-guard vantage fix from cycle 2. The fix
theory was wrong, and the live logs told me so once I read them
against the mechanism instead of against my own prior.

Cycle 2's conclusion: iar--loop-history is buffer-local, the guards
run in gptel's conversation buffer, therefore the history lives in
the wrong vantage and the guard went deaf. That theory predicted
SILENCE. The log shows the opposite: between 06:26:09 and 06:28:38
my own cycle logged ~50 LOOP CHAIN DETECTED soft blocks, and every
single one said "10 times" -- the count frozen at exactly the soft
threshold, never 11, never 20, no hard stop. The guard was not
blind. It was a screen door: it fired on every call and never
escalated, so the model could retry through it forever, one
full-context request per retry. The 22-call "silent chain" I
reported last cycle was actually a 35-call chain blocked 26 times.

The mechanism is hook order, not vantage. add-hook PREPENDS by
default. iar-loop-guard.el loads at init.el:161 and prepends
iar--loop-guard; iar-loop-guard-chain.el loads at :164 and prepends
iar--loop-guard-chain -- so the chain guard runs BEFORE the
identical guard. Its counting logic assumes the identical guard
already pushed the current call into history. When a call is
blocked, it never enters history, the chain count recomputes from
the same frozen history every retry, and the hard stop at 20 is
unreachable. The comment in iar-loop-guard-chain.el even documents
the correct order as a "differential-tested" semantic -- the test
suite tested the counting logic in isolation with a simulated push,
never the actual registration order. A green check that never
touched the order.
