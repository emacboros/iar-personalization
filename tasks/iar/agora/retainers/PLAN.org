* What a retainer is
A subordinate cycle-agent spawned by a citizen. Spawn file = entire
config (mandate, cadence, model, budget, task pointer, TTL,
done-condition). Owned by spawner; retainer READ-ONLY against it.
Spawn = write file, kill = remove file. No new systemd units.

* Caps (from D-010)
- 3 active per citizen; aggregate budget cap; cap exceeded = relay
  filing to Nacho.
- TTL 7d default; renewal = spawner touches the file.
- No spawn without checkable done-condition (loop-closer rule).
- Spawn/kill/renew visible in tool-call audit lines.

* Build order (proposed, small steps)
1. SPawn-file FORMAT spec (this tree, spawn-file-spec.org): fields,
   validation rules, done-condition grammar. Pure doc -- no runtime.
2. Model allowlist survey (model-allowlist.org): nemotron-3-ultra
   first candidate; survey = ollama pull + benchmark battery reuse
   (tool-call competence is the gate, not vibes).
3. Spawn registry (spawn-registry.org): one line per spawn
   (id, spawner, model, TTL, done-condition, state). Append-only.
4. Progress surface (progress-surface.org): where retainer output
   lands + how the citizen polls it.
5. FIRST SPAWN: emerges from citizen need (D-010: no pilot, no
   librarian). Candidate needs: census v3 classifier (recurring),
   digest assembly (Sep 14). Do NOT manufacture.

* Constraints
- Venue: all cycle work (D-005). Model composition changes stay
  interactive (D-008) -- allowlist SURVEY is data-gathering, not
  composition change.
- The retainer runtime itself (how a spawn file becomes a running
  agent) touches iar-agent-cycle.el -- that is .el code, so it is
  interactive-session work per the cycle rules. Cycles build the
  DOCS + registry + allowlist; the runtime lands in a session.
