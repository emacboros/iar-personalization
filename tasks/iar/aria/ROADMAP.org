* C67 FLAG-LOSS: MECHANISM FOUND (cycle 4, 2026-09-06) -- DO FIRST #1
- THE BUG (pinned by source read, not yet differential-tested):
  gptel--handle-wait (gptel-request.el:1899) resets per-request
  flags on :tool-result :tool-use :tool-calls-captured :error
  :http-status ... -- but NOT :stop-reason. When the cap hook
  returns (:block msg), gptel--handle-pre-tool sets
  (plist-put info :stop-reason reason) + :status "Stopped by hook"
  + :error reason. :error is reset by handle-wait on the NEXT
  request, but :stop-reason is NOT. gptel--error-p reads :error,
  so the FSM routes TYPE->DONE (no ERRS), and post-response fires
  with start==end (failed-request shape) => the handler's
  failed-request path counts a strike and sends NOTHING. The
  blocked call is retried by the MODEL (it sees the tool_call_error
  text), but the handler's continue logic never runs again after
  that text-only response unless... (the exact re-send path after a
  blocked call needs one more read: does the FSM re-send
  automatically after a blocked tool result, or does the handler
  need to? c67 evidence says the tool loop CONTINUED 17 calls after
  the arm => auto-re-send happens; the dead air came only at the
  final text-only response where the handler ran with the flag
  invisible).
- WHY THE WARN DIDN'T FIRE IN c67: same mechanism, earlier in the
  cycle. If :stop-reason leaked into info BEFORE the warn (from an
  earlier blocked call or an aborted request), the handler's
  failed-request path fired instead of the success path, and the
  tracker never incremented past the point where the state view
  diverged. ALTERNATIVE (simpler, still open): the warn DID fire
  but its :block was consumed by the same sticky :stop-reason
  path -- the model never saw the warning text. Journald sweep
  says zero "budget warning" MESSAGES -- but the message goes
  through (message) which in batch goes to stderr/journal; zero
  lines means the warn BRANCH never ran, i.e. :cap-warned was
  already t OR count never reached 60 in the state the cap hook
  saw. The sticky-:stop-reason mechanism explains the ARMED-flag
  loss; the warn silence may have the same root (state divergence)
  or a second one. Differential test will split these.
