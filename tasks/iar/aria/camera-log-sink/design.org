# Camera log sink -- design sketch (c225)

## Problem
The thingino logread ring is 312 lines and crond-heavy (the rssi cron
fires every 60s x8 cameras = most of the ring). During the 14:22L
house-wide go2rtc stall, the camera-side view (prudynt RTSP errors,
encoder state) rotated out within hours. The stall's camera-side
witness is unrecoverable. dmesg survives (kernel ring, bigger) but
only carries WiFi events, not RTSP/encoder state.

## Candidate designs
1. SOPHON PULLER (preferred): extend the rssi-puller.sh pattern --
   a 15min cron that SSH/HTTPs each camera's logread (thingino
   run.cgi recipe) and appends to /var/lib/aria-fleet/camlog/<ip>.log.
   Pros: no camera config changes, same shape as the proven puller,
   survives camera reboots. Cons: 15min granularity may still miss
   the exact stall-start minutes (logread ring holds ~5h of crond
   noise; without crond lines it holds much more).
2. Camera-side log file: thingino can write to /var (rssi.log
   persists across reboots). A camera-side cron appending filtered
   logread (grep -v crond) to /var/camlog would persist. Cons:
   per-camera config change, ring size limits.
3. Syslog to sophon: rsyslog already runs on sophon. Cameras would
   need remote-syslog config (thingino supports syslog? unverified).

## Recommendation
Start with (1): one sophon cron, zero camera changes, and it makes
the NEXT stall's camera-side view survivable at 15min granularity.
If a stall's start is missed again, add (2) on the two cameras that
matter most (.104 chronic encoder, .201 the stall's best witness).

## Verification
After deploy: force a stall-like condition? No -- just verify the
snapshot files grow and contain non-crond lines. Then wait for the
next stall (the three-check sequence + these snapshots = full
witness set).

## Filing
If (1) works with zero camera changes, no relay filing needed
(reversible, my domain). If (2)/(3) needed, file nacho-test.
