#+TITLE: Fix 2 design: delegate timeout vs live pipeline (c312)

Design for iar--delegate-timeout-handler (delegate.el), following
the c308 cascade crash (continuo 09-14, exit 255) and the c149
single-callback fix. Fix-1 (depth strip order) landed 763c7b3;
fix-3 (reqlog attribution) landed 792de9a. This is the last open
item from the cascade.

## The failure being fixed

The timeout handler fires at 600s while the delegate buffer's
pipeline is STILL STREAMING (live sub-agents making requests).
Current behavior: mark completed, gptel-abort the live request,
arm a 3s kill-buffer timer, callback the parent. The orphaned
sub-agents keep running; their completion hooks, re-prompt timers
(1s), and buffer-kill timers (3s/5s) race the abort/kill path.
A timer or curl sentinel hitting a dead/nil buffer raises
wrong-type-argument stringp nil -- the crash that killed the cycle.

## Design decision: DRAIN, not abort

The task file lists two options: (a) extend the timeout once with
a warning, or (b) drain -- wait for sub-requests to finish, then
complete with the partial result. Chosen: DRAIN, with a hard
ceiling. Reasons:

- A pipeline that is still streaming is doing REAL WORK. Aborting
  it destroys the sub-agents' output (the parent gets a timeout
  message; the work is lost). Draining preserves it.
- Extending "once with a warning" re-arms the same race at the new
  deadline if the pipeline is still live then. Drain-with-ceiling
  is the same idea but honest about the loop: keep draining while
  live, up to a ceiling, then hard-stop.
- The ceiling bounds the worst case: the parent's own delegate
  timeout was already 600s; the drain adds at most
  iar-delegate-drain-grace (default 300s) more. Total worst case
  900s per delegate -- still far below the cycle watchdog's
  1800s idle threshold (iar-agent-cycle.el resets idle on any
  active request, and drained sub-requests ARE active requests,
  so the cycle watchdog never sees a stall during a drain).

## Mechanism

1. New helper `iar--delegate-live-subrequests-p (buf)`:
   Returns non-nil if gptel--request-alist has any entry whose
   FSM :buffer is BUF (the delegate's own live curl request) --
   i.e. the delegate is actively streaming. This mirrors the
   lookup pattern gptel-abort itself uses (cl-find-if over
   gptel--request-alist, comparing (gptel-fsm-info fsm) :buffer
   to buf). A delegate with NO live request is between turns
   (re-prompt timer armed) or done -- aborting it is then safe
   (nothing is mid-stream; the 1s re-prompt timer is the only
   thing that could race, and it checks completed-sym and
   buffer-live-p before sending).

2. `iar--delegate-timeout-handler` rework (the `t` branch):
   - Mark completed-sym t (c149, unchanged).
   - If (iar--delegate-live-subrequests-p buf): do NOT abort.
     Arm a drain timer (1s tick) that re-checks liveness; when
     the request completes (the completion hook fires normally
     on DONE and delivers the real result), the drain timer
     sees no live request and exits without acting. If the
     drain exceeds iar-delegate-drain-grace (new defcustom,
     default 300), abort then -- the pipeline had its chance.
     The drain path NEVER calls the callback (the completion
     hook owns delivery); it only prevents the abort.
   - If NOT live: current behavior (abort + 3s kill timer +
     callback with partial/no response). This is the
     between-turns case: nothing streams, aborting is safe.

3. The 3s kill-buffer timer (abort path only): unchanged --
   it only fires in the not-live case, where no child stream
   is mid-flight against this buffer. (Children of a delegate
   buffer are separate buffers with their own lifecycles; the
   crash was specifically the delegate's OWN live request being
   aborted and its buffer killed under racing timers.)

4. New defcustom in configs/delegate.el:
   iar-delegate-drain-grace, default 300, :safe positive-integer-p.

## Why the drain path cannot double-callback

The drain path never touches completed-sym's callback flow: it
sets completed-sym BEFORE checking liveness (c149 order), so the
completion hook's entry guard is already armed. When the live
request finishes normally, the completion hook fires, sees
completed-sym non-nil, and skips -- WAIT, that would skip the
real result too.

CORRECTION (thinking it through): if we mark completed BEFORE
the drain, the completion hook will skip the genuine DONE and
the parent never gets the result. So the drain path must NOT
mark completed-sym. Revised order:

- Check liveness FIRST.
- If live: do NOT set completed-sym, do NOT abort. Arm drain
  timer. The timeout timer is effectively consumed (it fired
  once); the delegate now completes through its NORMAL path
  (completion hook on DONE -> callback). If the drain grace
  expires with the request still live, THEN mark completed +
  abort + callback (c149 path) -- the pipeline proved it is
  stuck past grace.
- If not live: c149 path unchanged (mark, abort, callback).

Double-callback safety: the completion hook and the
grace-expiry path both check completed-sym; exactly one of
them can be first (the other skips). The drain timer itself
never calls the callback.

## Edge cases

- Delegate buffer killed during drain: drain timer checks
  buffer-live-p; dead buffer -> c149 dead-buffer branch
  (callback with "killed before completion").
- Re-prompt timer fires during drain (text-only turn): the
  1s timer checks completed-sym (nil during drain) and
  buffer-live-p, then gptel-sends a new request. That new
  request becomes the live one the drain is waiting on. Fine.
- Nested delegates inside the draining delegate: they have
  their own timeout timers and their own drain logic (this
  fix applies at every depth). The depth strip (fix-1) caps
  how deep the tree grows.
- Drain grace expiry while a tool call is mid-execution
  (not a network request): request-alist only tracks network
  requests. A long-running synchronous tool (execute_code
  with a 600s timeout) would look "not live" between turns.
  Accept: the abort path handles it (c149 semantics), and
  tool timeouts are bounded by the tool layer.
