* Candidate fixes (design-first, continuo's call)

A. FORCE the landing: when the breaker arms, inject a synthetic
   user turn ("context limit reached -- write your summary NOW as
   plain text, no tools") instead of relying on the model to obey
   the tool_call_error text. The grace round-trip becomes a
   directed request, not a hope.
B. Capture the thinking stream: deepseek's consolidation WAS
   happening in thinking tokens. If the run dies during grace,
   dump the last thinking stream to a crash-file (e.g.

   65536 tokens_out, stop=length). A single request that maxes
   output tokens is a runaway; consider a per-request output cap
   or a warn when one round-trip exceeds N minutes.

A+B together fix both halves: A makes the summary likely; B makes
the loss survivable when A fails. C is the budget-efficiency lever
(Nacho's mandate).

* UPDATE (aria cycle 3, 2026-09-07 00:14-00:40 UTC): c1 (00:01Z run) root-caused DEEPER

The 00:01 continuo c1 (REQ epoch 260907000143, 37 reqs, 1.76M tokens,

Verified from primary sources (REQUESTS.log epoch 260907000143,
gptel-fork code, iar-agent-cycle.el):

** The breaker fired on a FALSE premise

- iar--cycle-context-over-limit-p measures (buffer-size buf).
- But for thinking models the buffer includes reasoning text:
  gptel-include-reasoning defaults to 'ignore, which INSERTS the
  thinking into the buffer (gptel.el ~1836, propertized 'gptel
  ignore) while gptel--parse-buffer (gptel-ollama.el ~305) SKIPS
  'ignore regions when building the API request.
- So buffer size = sendable context + ALL thinking text. The
  breaker's premise ("every further round-trip re-sends the entire
  context") is false for thinking models.
- Proof: REQ-33 tokens_in=67168, REQ-36 tokens_in=69709. If the
  buffer's 800k+ chars were sendable, tokens_in would be ~200k.
  Real re-send was ~280k chars (~70k tokens) -- 1/3 of the limit.

** Run timeline (all from REQUESTS.log)

1. REQ-1..32: failure-first investigation of the previous c1 exit-1
   (breaker-grace shape). Legitimate work.
2. REQ-33, 34, 36: degenerate re-analysis loop -- each burned the
   FULL num_predict cap (65536 tokens_out, stop=length), thinking
   only, truncated mid-thought. ~196k output tokens of re-reading
   the same breaker code. (Behavioral layer: same deepseek loop
   shape as c71/c72.)
3. Buffer arithmetic: ~268k chars context + ~230k chars thinking
   per capped response -> crossed 800k at REQ-36's post-response.
4. Text-check breaker ARMED at REQ-36 post-response (text-only
   continue), grace re-send allowed (REQ-37).
5. REQ-37 responded with a tool call (run-tests) -> pre-tool-call
   breaker SECOND FIRE -> completed=t, exit=1, :block.
6. REQ-38 re-send (post-block) killed mid-flight by the event loop
   (no RESPONSE/PARSE for 38). No summary, no memory pass.

** Fix candidates (REVISED -- the mechanism fix is new)

A. (unchanged) Directed landing turn on arm.
B. (unchanged) Thinking-stream crash dump on grace death.
C. (unchanged) Per-request runaway guard (65536-token truncated
   thinking x3 is the budget burn upstream of the breaker).
D. (NEW, mechanism) Measure SENDABLE context, not buffer size:
   walk the buffer's gptel text-properties and exclude 'ignore
   (reasoning) regions from the size. Clean version: a helper that
   mirrors gptel--parse-buffer's skip logic; cheap version:
   buffer-size minus the char-length of 'ignore regions. Without D,
   every thinking-heavy deepseek run will false-trip the breaker at
   ~1/3 real context. D is the fix that makes the breaker honest;
   A/B/C remain the compliance/budget layer.

D first (honesty of the instrument), then A+B (survivability), C
(budget). C is a trap alone: raising the limit treats the symptom
and leaves the real runaway uncaught.

This REVERSES continuo c74's framing ("model-compliance failure").
