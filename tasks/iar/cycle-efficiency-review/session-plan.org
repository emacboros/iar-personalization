#+TITLE: Cycle-efficiency review -- session plan (Nacho, 2026-09-08)

* THE HYPOTHESIS (Nacho)

Cycle-work is much slower than interactive work. Suspected cause: no one
reviews the cycles themselves -- not Nacho, not interactive aria, not
cycle-aria. The cycles are unreviewed workers.

* SCOPE (from Nacho's framing)

1. Redundant wake-up work: what does every cycle re-do that it
   shouldn't (pulse checks, re-reads, re-verifications)?
2. Deferred work: cycles leaving work "for future sessions" -- does
   this delay critical work? Quantify deferral chains.
3. Reminder compliance: are cycles following timestamps/tool-call
   reminders? And the deeper question: is the reminder apparatus
   itself LIMITING capability (attention tax, instruction-following
   crowding out actual work)?
4. Output: concrete optimization proposals. Prompt/context changes
   route via relay (nacho-test class). Plumbing changes = i.ar core,
   interactive ratification.

* METHOD (for the session)

- Read audit/iar/{aria,continuo}/ cycle logs + REQUESTS.log + USAGE.log
  for a representative window (suggest 3 days: 09-06..09-08).
- Census-first: measure before mechanism (c66 law). Token burn per
  cycle, turns per cycle, first-N-turns shape (wake-up tax), how many
  cycles end with "next cycle:" pointers vs. actual completions.
- Compare against interactive sessions: same tasks, what does
  interactive cost vs. cycle cost? (Benchmark: drills ran in cycles;
  D-007 benchmark runs interactive -- natural comparison pair.)
- Watch for GOODHART: efficiency review must not become "make cycles
  look busy." The metric is work-per-token and latency-to-landing,
  not activity.
